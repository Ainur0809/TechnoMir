# Junior

## Основы

**1. Что такое SQL? Что такое реляционная база данных?**
SQL (Structured Query Language) — язык запросов к реляционным базам. Реляционная БД хранит данные в **таблицах** (товары, заказы), а таблицы **связаны** между собой через ключи. «Реляция» = таблица/отношение. В «ТехноМире» 11 таблиц, связанных внешними ключами.

**2. DDL / DML / DCL — отличия и примеры.**
- **DDL** (Data Definition) — структура: `CREATE`, `ALTER`, `DROP`, `TRUNCATE`. Пример: `CREATE TABLE products (...)`.
- **DML** (Data Manipulation) — данные: `SELECT`, `INSERT`, `UPDATE`, `DELETE`.
- **DCL** (Data Control) — права: `GRANT`, `REVOKE`. Пример: `GRANT SELECT ON products TO shop_app`.
- (Ещё **TCL** — транзакции: `COMMIT`, `ROLLBACK`, `SAVEPOINT`.)

**3. Таблица, строка, столбец, схема.**
Таблица — набор данных об одной сущности (`products`). Строка (запись) — один объект (конкретный холодильник). Столбец (поле) — свойство (`price`). Схема — пространство имён, группа таблиц; в Postgres по умолчанию `public`.

**4. Что такое NULL? Почему `NULL = NULL` не работает?**
NULL — «значение неизвестно/отсутствует», это не 0 и не пустая строка. Любое сравнение с NULL даёт не TRUE/FALSE, а **UNKNOWN**, поэтому `NULL = NULL` → UNKNOWN, и `WHERE` такую строку отбрасывает. Проверять только через `IS NULL` / `IS NOT NULL`. В «ТехноМире»: `WHERE phone = NULL` вернёт 0 строк, а `WHERE phone IS NULL` — покупателей без телефона.

**5. DELETE vs TRUNCATE vs DROP.**
- `DELETE FROM t WHERE ...` — удаляет строки по условию (DML), можно откатить, срабатывают триггеры.
- `TRUNCATE t` — быстро очищает **всю** таблицу (DDL), не по строкам. В Postgres откатывается в транзакции, в MySQL — нет.
- `DROP TABLE t` — удаляет **саму таблицу** со структурой.
Коротко: DELETE — часть строк, TRUNCATE — все строки, DROP — таблицу целиком.

**6. Ключи. Primary key, Foreign key.**
- **Primary key** — уникально идентифицирует строку, не NULL, один на таблицу (`products.id`).
- **Foreign key** — ссылка на PK другой таблицы, обеспечивает целостность (`orders.customer_id → customers.id`): нельзя создать заказ несуществующего покупателя.

**7. Связи 1:N и N:M. Как реализуется N:M?**
- **1:N** (один-ко-многим): один покупатель — много заказов. FK ставится на стороне «многих» (`orders.customer_id`).
- **N:M** (многие-ко-многим): заказ содержит много товаров, товар — во многих заказах. Напрямую не хранится — нужна **связующая таблица**. В «ТехноМире» это `order_items` (между orders и products) и `product_suppliers` (между products и suppliers).

**8. Что такое COMMIT?**
Команда, фиксирующая транзакцию: все изменения с начала транзакции становятся постоянными и видны другим. До `COMMIT` их можно отменить через `ROLLBACK`.

**9. Что такое бэкап? Зачем нужен?**
Резервная копия данных для восстановления после сбоя, ошибки или удаления. В «ТехноМире» (часть 7.3): `pg_dump shop > backup.sql` создаёт копию, `psql shop_copy < backup.sql` восстанавливает. Важно: бэкап бесполезен, пока не проверено восстановление.

## Выборка

**10. SELECT / INSERT / UPDATE / DELETE — синтаксис.**
```sql
SELECT name, price FROM products WHERE stock > 0;
INSERT INTO brands (name, country) VALUES ('Haier', 'Китай');
UPDATE products SET price = price * 1.1 WHERE category_id = 3;
DELETE FROM reviews WHERE rating = 1;
```
⚠️ UPDATE/DELETE без `WHERE` затронут **всю** таблицу.

**11. WHERE: сравнения, AND/OR/NOT, IN, BETWEEN.**
`=, <>, <, >, <=, >=`; `AND/OR/NOT` объединяют условия; `IN (1,2,3)` — любое из списка; `BETWEEN 1000 AND 5000` — диапазон включительно. Пример: `WHERE price BETWEEN 10000 AND 50000 AND stock > 0`.

**12. LIKE и шаблоны `%` и `_`.**
`%` — любое число любых символов, `_` — ровно один символ. `name LIKE 'Холод%'` — начинается с «Холод». `LIKE '%сон%'` — содержит «сон». В Postgres `LIKE` чувствителен к регистру, `ILIKE` — нет.

**13. ORDER BY, LIMIT / OFFSET.**
`ORDER BY price DESC, name ASC` — сортировка (DESC — по убыванию). `LIMIT 10 OFFSET 20` — 10 строк, пропустив первые 20 (пагинация, 3-я страница). В SQL Server — `TOP`, в стандарте — `FETCH FIRST 5 ROWS ONLY`.

**14. DISTINCT.**
Убирает дубликаты из результата. `SELECT DISTINCT city FROM addresses` — уникальные города.

**15. Агрегатные функции.**
`COUNT` — количество, `SUM` — сумма, `AVG` — среднее, `MIN`/`MAX` — минимум/максимум. `SELECT AVG(price), MAX(price) FROM products`.

**16. GROUP BY — зачем?**
Группирует строки по значению столбца, чтобы считать агрегаты **по каждой группе**. `SELECT category_id, COUNT(*) FROM products GROUP BY category_id` — сколько товаров в каждой категории.

**17. COUNT(*) vs COUNT(column).**
`COUNT(*)` — все строки. `COUNT(column)` — только строки, где столбец **не NULL**. `COUNT(DISTINCT column)` — уникальные непустые значения. В «ТехноМире»: `COUNT(*)` = 30 покупателей, `COUNT(phone)` = 26 (четверо без телефона).

**18. JOIN: INNER / LEFT / RIGHT / FULL / CROSS.**
- **INNER** — только совпавшие строки обеих таблиц.
- **LEFT** — все строки левой + совпавшие правой (нет пары → NULL). Пример: все покупатели и их заказы, включая тех, у кого 0 заказов.
- **RIGHT** — зеркально, все строки правой.
- **FULL** — все строки обеих таблиц.
- **CROSS** — декартово произведение (каждая с каждой), без условия.

**19. Как найти записи «за сегодня» / за период.**
```sql
WHERE created_at >= CURRENT_DATE;                          -- сегодня
WHERE created_at >= '2026-10-01' AND created_at < '2026-11-01';  -- октябрь
```
⚠️ Ловушка: `BETWEEN '2026-10-01' AND '2026-10-31'` для `TIMESTAMP` теряет 31 октября после 00:00 — граница это полночь. Надёжнее полуоткрытый интервал `>= начало AND < следующий месяц`.

## Практика QA

**20. Как проверить, что данные из UI/API попали в БД?**
После действия в UI делаешь `SELECT` и сверяешь: появилась ли строка, верные ли значения, проставились ли `created_at`/статус, сработали ли связи (у заказа есть позиции). Это проверка на стыке: UI говорит «успех», а в базе данные должны реально лежать и быть корректными.

**21. Что такое SQL injection? Как проверить поле?**
Атака, когда ввод пользователя склеивается в текст SQL и становится командой. Проверка поля: подать одиночную кавычку `'` — если прилетает SQL-ошибка или 500, поле уязвимо. Затем `' OR '1'='1' --`. Защита — параметризованные запросы. Подробно — в [injection.md](../injection.md) и демо на Java в [part8_injection/](../part8_injection/).

**22. SQL vs NoSQL — базово.**
SQL — реляционные БД, строгая схема, таблицы, связи, транзакции ACID (PostgreSQL, MySQL). NoSQL — гибкая/без схемы, документы/ключ-значение/графы, горизонтальное масштабирование (MongoDB, Redis). SQL — когда важна целостность и сложные связи (магазин, банк); NoSQL — когда важны объём, скорость и гибкость структуры (логи, кэш, ленты).

# Middle

## Структура и целостность

**1. Нормализация (1НФ–3НФ) и денормализация.**
Нормализация — разложение данных по таблицам, чтобы убрать дублирование и аномалии.
- **1НФ** — каждое поле атомарно (не список в одной ячейке), есть ключ.
- **2НФ** — 1НФ + каждый неключевой столбец зависит от **всего** составного ключа.
- **3НФ** — 2НФ + нет зависимостей между неключевыми столбцами (бренд вынесен в `brands`, а не продублирован в `products`).
**Денормализация** — осознанное дублирование ради скорости чтения (меньше JOIN). Оправдана в отчётах/аналитике, где важна скорость, а не частые изменения. Пример компромисса в «ТехноМире»: `orders.total` хранится, хотя его можно пересчитать из позиций.

**2. Ограничения: NOT NULL, UNIQUE, CHECK, DEFAULT.**
- `NOT NULL` — поле обязательно (`email`).
- `UNIQUE` — значения не повторяются (`customers.email`).
- `CHECK` — условие на значение (`CHECK (price > 0)`, `CHECK (rating BETWEEN 1 AND 5)`).
- `DEFAULT` — значение по умолчанию (`status DEFAULT 'new'`, `created_at DEFAULT CURRENT_TIMESTAMP`).
Все они есть на таблице `products` в «ТехноМире».

**3. Composite key. Surrogate vs natural key.**
- **Composite (составной)** ключ — PK из нескольких столбцов. В «ТехноМире» — `product_suppliers (product_id, supplier_id)`.
- **Surrogate** — искусственный ключ без смысла (`id SERIAL`). **Natural** — осмысленный из данных (email, ИНН). Суррогатный стабильнее (email может поменяться), поэтому обычно берут его.

**4. ON DELETE CASCADE / SET NULL / RESTRICT.**
Что будет с дочерними строками при удалении родителя:
- **CASCADE** — удалить вместе (удалил покупателя → ушли его заказы).
- **SET NULL** — обнулить ссылку (удалил категорию → товар остался, `category_id = NULL`).
- **RESTRICT** — запретить удаление, пока есть дети (нельзя удалить бренд с товарами).

**5. Как тестировать каскадные эффекты.**
Создать родителя с детьми → удалить/обновить родителя → проверить `SELECT`'ом, что с детьми произошло ожидаемое (удалились при CASCADE, обнулились при SET NULL, удаление отклонено при RESTRICT). Проверять в транзакции с `ROLLBACK`, чтобы не портить данные.

## Выборка углублённо

**6. Порядок выполнения SELECT.**
Логический порядок: `FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`. Поэтому алиасы из `SELECT` нельзя использовать в `WHERE` (он выполняется раньше), а агрегаты нельзя в `WHERE` (группировки ещё нет).

**7. WHERE vs HAVING.**
`WHERE` фильтрует **строки до** группировки, `HAVING` — **группы после** агрегатов. `WHERE AVG(rating) > 4` — ошибка (агрегата ещё нет), правильно `HAVING AVG(rating) > 4`.

**8. UNION vs UNION ALL.**
Оба склеивают результаты двух запросов (нужно одинаковое число и типы столбцов). `UNION` **убирает дубликаты** (сортирует/хеширует — медленнее), `UNION ALL` оставляет всё как есть (быстрее). Если дублей нет или они не мешают — `UNION ALL`.

**9. Подзапросы: в WHERE / FROM / SELECT. Коррелированный.**
- В `WHERE`: `WHERE price > (SELECT AVG(price) FROM products)`.
- В `FROM`: подзапрос как временная таблица.
- В `SELECT`: вычисляемый столбец.
**Коррелированный** — подзапрос ссылается на внешний и выполняется для **каждой** строки (`WHERE p.price > (SELECT AVG(price) FROM products WHERE category_id = p.category_id)`). Медленнее обычного.

**10. EXISTS vs IN.**
`IN` сравнивает со списком значений, `EXISTS` проверяет, вернул ли подзапрос хоть строку. `EXISTS` часто быстрее на больших/коррелированных подзапросах и **корректнее с NULL**: `NOT IN` при NULL в списке вернёт пусто, `NOT EXISTS` — нет. Для «есть ли связанные строки» бери `EXISTS`.

**11. CASE WHEN.**
Условная логика в запросе:
```sql
CASE WHEN price < 1000 THEN 'дешёвый'
     WHEN price <= 20000 THEN 'средний'
     ELSE 'дорогой' END AS segment
```

**12. Как найти дубликаты.**
```sql
SELECT email, COUNT(*) FROM customers GROUP BY email HAVING COUNT(*) > 1;
```
Группировка по полю + `HAVING COUNT(*) > 1`.

**13. N-я по величине / последняя по дате.**
```sql
-- 2-я по цене
SELECT DISTINCT price FROM products ORDER BY price DESC LIMIT 1 OFFSET 1;
-- или оконкой: ранжируем и берём rn = 2
SELECT * FROM (SELECT *, DENSE_RANK() OVER (ORDER BY price DESC) rn FROM products) t WHERE rn = 2;
-- последний заказ покупателя
SELECT * FROM orders WHERE customer_id = 1 ORDER BY created_at DESC LIMIT 1;
```

**14. Записи, которые есть в одной таблице, но нет в другой.**
```sql
SELECT c.* FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;              -- покупатели без заказов
```
`LEFT JOIN` + `WHERE правая.pk IS NULL`, либо `NOT EXISTS`.

**15. Self join — когда?**
Когда таблица связана сама с собой. В «ТехноМире» `categories.parent_id → categories.id`: вывести категорию и её родителя одной строкой — `JOIN categories parent ON parent.id = c.parent_id`.

**16. View (представление). Можно ли обновлять через view?**
View — сохранённый `SELECT`, виртуальная таблица; данные **не хранит**, считает на лету. Упрощает сложные запросы и ограничивает доступ. Простые view (из одной таблицы, без агрегатов) обновляемы; view с JOIN/GROUP BY/агрегатами — нет (только через INSTEAD OF триггеры). В «ТехноМире» — `v_order_summary`, `v_product_stats` (часть 7).

**17. Функции в SQL.**
- **Встроенные:** строковые (`UPPER`, `LENGTH`, `SUBSTRING`, `||`), числовые (`ROUND`, `ABS`), дата/время (`NOW`, `DATE_TRUNC`, `EXTRACT`), NULL-функции (`COALESCE`, `NULLIF`).
- **Пользовательские (UDF)** — свои функции. В «ТехноМире» — `place_order(...)` на PL/pgSQL.

**18. Процедуры vs функции vs триггеры.**
- **Функция** — возвращает значение, вызывается в `SELECT`.
- **Процедура** — выполняет действия, может управлять транзакцией (`CALL`), не обязана возвращать значение.
- **Триггер** — код, который БД запускает **автоматически** при INSERT/UPDATE/DELETE. В «ТехноМире» (часть 9.10) — триггер списывает `stock` при вставке в `order_items`.

## Транзакции

**19. Транзакция. ACID.**
Транзакция — группа операций «всё или ничего».
- **Atomicity** — либо все шаги, либо ни одного (сбой при оформлении заказа → откат всего).
- **Consistency** — БД переходит из корректного состояния в корректное (ограничения не нарушаются).
- **Isolation** — параллельные транзакции не мешают друг другу.
- **Durability** — после COMMIT данные сохранены даже при сбое питания.

**20. COMMIT vs ROLLBACK. SAVEPOINT.**
`COMMIT` — зафиксировать, `ROLLBACK` — отменить все изменения транзакции. `SAVEPOINT` — метка внутри транзакции; `ROLLBACK TO SAVEPOINT` откатывает частично, до метки, не отменяя всю транзакцию.

**21. Autocommit.**
Режим, когда каждая команда — отдельная транзакция, фиксируется сразу. Включён по умолчанию в большинстве клиентов. При нём `ROLLBACK` без явного `BEGIN` ничего не откатит. Для ручных экспериментов с транзакциями autocommit отключают (в DBeaver — переключатель Manual Commit).

## Индексы

**22. Что такое index? B-tree базово.**
Индекс — вспомогательная структура для быстрого поиска, как алфавитный указатель в книге. Обычно **B-tree** — сбалансированное дерево, где поиск идёт по уровням, поэтому сложность `O(log n)`, а не полный перебор `O(n)`.

**23. Когда индекс помогает, когда вредит.**
Помогает чтению: `WHERE`, `JOIN`, `ORDER BY` по индексированному столбцу. Вредит записи: каждый `INSERT/UPDATE/DELETE` должен обновить ещё и индексы — вставка медленнее, индекс занимает место. Поэтому индексируют то, по чему часто ищут, а не всё подряд.

**24. Unique index vs обычный.**
Unique дополнительно **запрещает дубликаты** в столбце (его автоматически создаёт `UNIQUE`/`PRIMARY KEY`). Обычный только ускоряет поиск.

**25. EXPLAIN / план запроса.**
`EXPLAIN` показывает, как БД собирается выполнять запрос; `EXPLAIN ANALYZE` — ещё и реально выполняет и даёт время. По плану видно `Seq Scan` (полный перебор — индекс не используется) или `Index Scan` (по индексу). В «ТехноМире» часть 5: на 100 000 строк видно переход Seq Scan → Index Scan после создания индекса.

## Практика QA

**26. Миграция данных. Что проверять.**
Перенос данных из старой структуры/системы в новую. Проверять: **полноту** (совпадает `COUNT`), **целостность** (связи не битые), **типы и форматы** (даты, числа), **кодировки** (не поломались русские буквы), выборочную сверку значений, отсутствие дублей.

**27. Подготовка тестовых данных и откат.**
Варианты: seed-скрипт (как `02-data.sql`), фикстуры, фабрики. Откат: выполнять тест в транзакции с `ROLLBACK`, либо пересоздавать БД (`docker compose down -v && up`), либо точечно удалять созданное. В «ТехноМире» запросы части 3 обёрнуты в `BEGIN ... ROLLBACK`, чтобы не портить данные.

**28. Что такое ORM? Зачем SQL, если есть ORM?**
ORM (Hibernate, SQLAlchemy) отображает таблицы на объекты кода, генерирует SQL автоматически. Но: нужно понимать сгенерированный SQL для отладки, оптимизации (N+1, индексы), для сложных запросов и аналитики пишут SQL руками, а тестировщик всё равно проверяет данные напрямую в БД.

**29. Как найти «мусорные» данные после тестов.**
Запросы-проверки целостности (как в `practice/tasks.md`, уровень QA): заказы без позиций, платежи ≠ сумме заказа, отзывы на неполученный товар, осиротевшие записи, нарушенные статусы. В идеале такие запросы возвращают 0 строк.

**30. Защита от SQL injection.**
Главное — **параметризованные запросы / prepared statements**: ввод передаётся отдельно от текста SQL и всегда трактуется как данные. Плюс валидация ввода, минимальные права пользователя БД, не показывать текст SQL-ошибок, хранить пароли хэшем. Ручное экранирование кавычек — ненадёжно. Демо — часть 8.

# Senior

## Транзакции и конкурентность

**1. Уровни изоляции.**
От слабого к строгому: **READ UNCOMMITTED** (видно незафиксированное — dirty read), **READ COMMITTED** (видно только зафиксированное; по умолчанию в Postgres), **REPEATABLE READ** (в рамках транзакции данные не меняются), **SERIALIZABLE** (как будто транзакции выполняются по очереди). Чем строже — тем меньше аномалий, но больше блокировок/откатов.

**2. Аномалии.**
- **Dirty read** — чтение незафиксированных чужих изменений.
- **Non-repeatable read** — один и тот же `SELECT` в транзакции вернул разное (чужой COMMIT между ними).
- **Phantom read** — повторный запрос по условию вернул новые строки.
- **Lost update** — две транзакции перезаписали значение, одно изменение потерялось.
Воспроизводятся двумя сессиями (в «ТехноМире» часть 6.3 и 6.7). Тестируются выставлением `SET TRANSACTION ISOLATION LEVEL ...` и проверкой, пропадает ли аномалия.

**3. Deadlock.**
Две транзакции взаимно ждут ресурсы друг друга (T1 держит A и ждёт B, T2 держит B и ждёт A). БД обнаруживает цикл и **откатывает одну** транзакцию с ошибкой deadlock. Защита: блокировать ресурсы всегда в одном порядке (в «ТехноМире» товары в заказе блокируются по возрастанию id — часть 6.6).

**4. Оптимистичная vs пессимистичная блокировка.**
- **Пессимистичная** — сразу блокирует строку (`SELECT ... FOR UPDATE`), другие ждут. Подходит при частых конфликтах.
- **Оптимистичная** — не блокирует, а при сохранении проверяет версию (`version`/timestamp); если изменилось — ошибка и повтор. Подходит, когда конфликты редки.

**5. MVCC.**
Multi-Version Concurrency Control: БД хранит несколько версий строки, читатели видят снимок данных и **не блокируют** писателей (и наоборот). Так Postgres обеспечивает изоляцию без тотальных блокировок на чтение.

**6. Lock и типы.**
Блокировка защищает данные при параллельном доступе. По объёму: **row** (строка) / **table** (таблица). По режиму: **shared** (S, на чтение — несколько читателей одновременно) / **exclusive** (X, на запись — монопольно).

## Индексы и производительность

**7. Clustered vs non-clustered.**
**Clustered** — сами данные физически упорядочены по ключу индекса (один на таблицу; в MySQL/InnoDB — по PK). **Non-clustered** — отдельная структура со ссылками на строки (их много). В Postgres «чистого» clustered нет, есть команда `CLUSTER`.

**8. Composite index: порядок столбцов, left-most prefix.**
Индекс по нескольким столбцам `(a, b)` работает для условий по `a` и по `a AND b`, но **не** по одному `b` — нужен ведущий (левый) столбец. Поэтому порядок важен: первым ставят самый селективный/часто используемый в фильтрах.

**9. Covering, partial, на выражении.**
- **Covering** — индекс содержит все нужные запросу столбцы, можно ответить без обращения к таблице (`INCLUDE`).
- **Partial** — индекс по части строк (`WHERE active = true`), меньше и быстрее.
- **На выражении (функциональный)** — `CREATE INDEX ON products(LOWER(name))`, чтобы работал поиск по `WHERE LOWER(name) = ...`.

**10. Почему запрос не использует индекс.**
- **Функция над столбцом**: `WHERE LOWER(name) = ...` — обычный индекс по `name` не подходит (нужен функциональный).
- **Неявное приведение типов** (строка vs число).
- **LIKE '%...'** с `%` в начале — индекс по префиксу не работает.
- Таблица маленькая — планировщик сам выбирает Seq Scan.
- Низкая селективность (см. п. про status).

**11. Как читать EXPLAIN ANALYZE.**
`Seq Scan` — полный перебор (плохо на больших таблицах), `Index Scan` — по индексу. Соединения: `Nested Loop` (хорошо на малых объёмах), `Hash Join` (на больших), `Merge Join` (по отсортированным). Смотрят оценочные vs реальные строки (`rows`), время и где теряется больше всего.

**12. N+1 problem.**
1 запрос за списком + по 1 запросу на каждый элемент (частый косяк ORM): 1 запрос за заказами + N запросов за позициями каждого. Обнаружить — по логу запросов (много однотипных). Устранить — один `JOIN` или пакетная загрузка (`WHERE id IN (...)`, `JOIN FETCH`).

**13. Как оптимизировать медленный запрос.**
Найти через **slow query log** / мониторинг → `EXPLAIN ANALYZE` → понять узкое место (Seq Scan, дорогой JOIN, сортировка) → добавить индекс, переписать запрос, убрать функции из WHERE, ограничить выборку. Проверить план до/после.

**14. Партиционирование.**
Разбиение большой таблицы на части (по дате, диапазону, хешу). Запросы по ключу партиции читают только нужную часть, старые партиции легко архивировать/удалять. Нужно на таблицах в десятки-сотни млн строк.

## Продвинутые запросы

**15. Window functions.**
Считают по «окну» строк, **не схлопывая** их в одну (в отличие от GROUP BY). `ROW_NUMBER` — номер строки, `RANK` — ранг с пропусками при равенстве, `DENSE_RANK` — без пропусков, `LAG/LEAD` — значение из предыдущей/следующей строки, `PARTITION BY` — разбивка на группы. Пример: `ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY price DESC)` — нумерация товаров внутри категории.

**16. CTE (WITH) и рекурсивные. CTE vs подзапрос vs temp.**
CTE — именованный подзапрос перед основным, читаемее вложенных. **Рекурсивный** (`WITH RECURSIVE`) — для деревьев/иерархий (всё дерево категорий «ТехноМира»). CTE vs подзапрос — в основном читаемость; временная таблица **материализуется** и переиспользуется в нескольких запросах (CTE живёт один запрос).

**17. MERGE / UPSERT.**
«Вставить или обновить». Postgres: `INSERT ... ON CONFLICT (email) DO UPDATE SET ...`; MySQL: `ON DUPLICATE KEY UPDATE`. Нужно, когда не знаешь заранее, есть ли уже запись (синхронизация, импорт).

**18. JSON в реляционной БД.**
Postgres умеет тип `jsonb`: хранить полуструктурированные данные, обращаться к полям (`data->>'key'`), индексировать (GIN). Удобно для гибких атрибутов, но не замена нормальной схемы — по JSON сложнее валидировать и связывать.

## Архитектура и надёжность

**19. Репликация. Lag.**
Копирование данных на другие серверы. **Master-slave** — пишем в master, читаем со slave (масштабирование чтения). **Master-master** — пишем в несколько (сложнее, конфликты). **Lag репликации** — задержка, с которой реплика догоняет master; для тестов опасно: записал в master, тут же прочитал с реплики — данных ещё нет (ложный баг).

**20. Шардирование.**
Горизонтальное разбиение данных по разным серверам (шардам) по ключу (например, по региону). Масштабирует запись и объём, но усложняет: запросы между шардами, уникальность id, транзакции через шарды, ребалансировка.

**21. Стратегии бэкапа.**
- **Full** — полная копия.
- **Incremental** — только изменения с последнего любого бэкапа (экономно, восстановление по цепочке).
- **Differential** — изменения с последнего full.
**Point-in-time recovery** — восстановление на конкретный момент (full + WAL-логи). Бэкап рабочий только если **проверено восстановление** на тестовой базе.

**22. Миграции схемы (Flyway / Liquibase).**
Инструменты версионирования схемы: изменения описываются пронумерованными скриптами, применяются по порядку, хранится история. Дают rollback и **zero-downtime** миграции (обратно совместимые шаги: сначала добавить столбец nullable, потом заполнить, потом сделать NOT NULL), чтобы не ронять прод.

**23. Тестирование миграции на большом объёме.**
Сверка `COUNT` до/после, **checksum**/хеш по строкам или колонкам, выборочная сверка записей, проверка граничных и «проблемных» данных (NULL, кодировки, длинные строки), замер времени миграции на объёме, близком к боевому.

**24. CAP-теорема. Eventual vs strong consistency.**
В распределённой системе при разрыве сети (**P**) нельзя одновременно иметь и **C** (консистентность), и **A** (доступность) — выбираешь одно. **Strong consistency** — все видят одно и то же сразу (банки). **Eventual** — данные «сойдутся» со временем (ленты соцсетей); быстрее и доступнее, но возможен рассинхрон.

**25. SQL vs NoSQL — критерии выбора.**
SQL: нужны сложные связи, транзакции, строгая целостность, отчётность (магазин, финансы). NoSQL: огромный объём/нагрузка, гибкая или меняющаяся структура, горизонтальное масштабирование, простые запросы по ключу (кэш, логи, каталоги, ленты). Часто используют вместе.

## Безопасность

**26. Виды SQL injection. Защита на всех уровнях.**
- **Classic** — данные сразу в ответе (`UNION SELECT`).
- **Blind** — ответ только да/нет, данные вытаскивают по биту/букве.
- **Time-based** — ответа не видно, но по задержке (`pg_sleep`) понятно true/false.
- **Second-order** — payload сохраняется и срабатывает позже, при другом запросе.
Защита слоями: параметризованные запросы (главное) + валидация ввода + минимальные права + не показывать SQL-ошибки + хэш паролей + WAF. Все виды разобраны в [injection.md](../injection.md).

**27. Права доступа. Минимальные привилегии.**
`GRANT` выдаёт права, `REVOKE` забирает. **Принцип минимальных привилегий**: у приложения/пользователя только то, что нужно (например, `SELECT/INSERT/UPDATE`, без `DROP` и без доступа к `password_hash`). Отдельные пользователи для приложения, для тестов, для аналитики. В «ТехноМире» — роль `shop_app` (часть 9.7): даже успешная инъекция не удалит таблицу и не прочитает хэши.

## Практика QA

**28. Стратегия тестирования слоя БД.**
- **Unit** — отдельные функции/процедуры/триггеры, проверки ограничений.
- **Integration** — приложение + реальная БД: прошёл ли путь UI/API → БД.
- **Data quality** — запросы-проверки целостности (осиротевшие строки, несходящиеся суммы, дубли).
Плюс: тесты миграций, прав доступа, инъекций, производительности.

**29. Тестовая БД в CI.**
Поднимать БД в **контейнере** (Docker / Testcontainers) на каждый прогон → накатывать схему и **seed-данные** (фикстуры) → тесты в **изоляции** (каждый в транзакции с откатом, или своя схема/БД) → после прогона контейнер убивать. Как в «ТехноМире»: Docker + `initdb/` дают воспроизводимую базу одной командой.

**30. Тестирование производительности под нагрузкой.**
Залить реалистичный объём (как 100 000 строк в части 5), гонять нагрузку (JMeter / k6 / pgbench), замерять время ответа, throughput, использование CPU/IO, рост при конкуренции. Искать деградацию, блокировки, медленные запросы (`EXPLAIN ANALYZE`, slow log).

**31. Сверка данных между БД / после ETL.**
Сверка `COUNT` по таблицам, агрегатов (`SUM` ключевых метрик), **checksum/хеш** построчно или по колонкам, выборочная сверка записей, проверка по ключам «есть там — нет тут» (`LEFT JOIN ... IS NULL` / `EXCEPT`). Фиксировать расхождения и разбирать причину.
